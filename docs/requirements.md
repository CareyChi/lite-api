# lite-api 产品需求文档

文档状态：初版需求基线。项目阶段：工程初始化；本文所列功能除明确说明外均尚未交付。

## 1. 产品定位与目标

lite-api 是面向个人开发者、团队及授权服务提供者的可自托管 AI API 网关，融合多渠道聚合、统一密钥管理、模型路由、账号池调度、额度计费及可观测性。设计借鉴 New API 与 Sub2API 的功能模式，但不依赖其业务代码。

目标：
- 使用一个网关地址统一管理多个 AI 服务商及授权上游。
- 同时兼容主流原生 API 和明确受限的跨协议转换。
- 能根据模型能力、健康状态、优先级、权重、成本和并发限制调度上游账号。
- 用可审计的账本结算用量，在长连接、失败重试及断线场景保证一致性。
- 可先在单机部署，之后通过共享 PostgreSQL/Redis 扩展至多节点。

非目标：绕过上游身份验证、批量滥用消费级账号、规避上游使用条款；不承诺不同厂商的所有语义可以无损互转。

## 2. 用户角色

- 系统管理员：配置用户、模型、上游、账号池、计费规则、风控及运维。
- 普通用户：管理自己拥有的 API Key、查看可用模型、用量、余额和请求记录。
- API 客户端：通过标准 SDK、Claude Code、Codex、OpenCode 等已支持的协议访问网关；具体兼容度由测试矩阵决定。

## 3. 功能范围与优先级

### P0：核心 MVP

**FR-01 用户与访问密钥**
- 管理员和普通用户角色；API Key 可创建、列出摘要、停用、吊销。
- 明确 Key 归属、到期时间、允许模型、额度限制；密钥明文仅创建时显示一次。
- 网关鉴权与管理后台鉴权隔离；所有管理动作记录审计事件。

**FR-02 上游渠道与模型**
- 渠道配置：Provider 类型、受允许的 Base URL、凭据、模型列表、别名映射、优先级、权重、启停。
- 账号具有独立的凭据、并发限制、健康状态与冷却时间；不把上游账号等同于前台用户。
- 为同一逻辑模型绑定多个上游模型及能力标签（流式、工具、思考、视觉、缓存等）。

**FR-03 原生协议入口**
- OpenAI Chat Completions、Responses、Models；Anthropic Messages；Gemini GenerateContent/streamGenerateContent。
- 支持常规请求及流式响应，保留有效的状态码、事件类型、工具调用与用量信息。
- 同协议原生透传优先；跨协议转换须有逐项能力映射和回归测试，无法支持则返回明确错误。

**FR-04 请求路由与账号池**
- 基于可用模型、协议能力、分组、优先级、权重、健康度和并发槽筛选上游。
- 支持单请求幂等标识、有限重试、熔断冷却、粘性会话、降级和回退策略。
- Redis 原子维护分布式并发槽位；异常退出具有过期或租约回收机制。
- 发生流式响应后禁止自动跨上游重发生成请求。

**FR-05 限流与配额**
- 基于用户、API Key、渠道、账号分别限制 RPM、TPM、最大并发和余额配额。
- 超限时提供标准化错误及可合理计算的重试提示，不泄露其他用户的限制。
- Redis 负责高频判定，PostgreSQL 负责持久配置和账务事实。

**FR-06 计费和账本**
- 各模型支持输入、输出、缓存读、缓存写和特殊计费项；价格使用精确十进制或整数最小单位。
- 请求预留额度、实际用量结算、差额释放、失败退款构成可审计的业务链路。
- 对账本事务、幂等键和异步重复消费进行专门测试。
- 区分上游返回的真实 Token 与网关估算 Token，不能将估算伪装为精确计费数据。

**FR-07 管理控制台**
- 管理员：渠道、模型、用户、账号池、密钥、配额、使用记录、运行状态。
- 普通用户：可用模型、密钥、余额/配额、调用历史。
- 状态和图表必须读取真实 API 数据；未实现页面不显示为已可用。

**FR-08 观测、审计与安全**
- 每个请求具有 request_id；记录渠道、模型、状态、耗时、Token、费用、失败原因。
- 默认不记录提示词/响应正文；日志中的秘密数据需脱敏。
- 上游地址必须做 SSRF 防护；合理限制重定向、代理头信任和后台访问权限。
- 提供健康检查、优雅停机及持久化数据库备份方案。

### P1：增强阶段

- Token/凭据刷新、Redis Streams 异步任务、批量模型同步及监控告警。
- 更完整的跨协议转换、视觉与工具流事件、Thought/Reasoning 和缓存计费。
- 模型定价版本管理、数据归档与账单导出。
- 通过 Docker Compose 部署 API + 前端 + PostgreSQL + Redis。
- 按产品需要增加订阅套餐与额度管理，不默认接入任何支付机构。

### P2：规模化与商业化

- 多网关实例、统一配置分发、更多高级路由策略。
- Prometheus、Grafana、OpenTelemetry 分布式追踪。
- 自助充值、支付回调、兑换码、通知系统与运营报表（在明确支付及合规要求后实施）。
- 多租户和更细粒度 RBAC（若实际业务需要）。

## 4. 关键流程与业务规则

### 4.1 请求生命周期

1. 校验客户端密钥、权限与参数。
2. 确定逻辑模型和协议能力，预估/预留额度。
3. 取得速率令牌、并发槽位与上游账号租约。
4. 构造原生请求或受支持的协议转换，透传到上游。
5. 持续转发流式内容并跟踪取消信号。
6. 记录实际用量，完成幂等结算并归还槽位；异常时完成明确的补偿。

### 4.2 路由与故障行为

- 能力不符合的账号不得进入候选池。
- 同等优先级按权重调度；调度必须对并发和健康度敏感。
- 429、账户额度耗尽、可恢复网络错误有区分的冷却与重试策略。
- 只有在尚未发送下游响应且请求允许重放时，才可切换上游。
- 粘性会话必须有限期且只在账号仍可用、仍支持所选能力时生效。

### 4.3 计费一致性

- 余额不能因为重试、异步重复投递、客户端断开而重复扣减。
- 上游未回报 Token 时，需要有独立且可追溯的估算/人工对账策略。
- 审计中保留价格版本、用量来源及请求状态；不可用 Redis 数值覆盖 PostgreSQL 账本。

## 5. 非功能约束

- 技术方案：Go + Gin + Ent/pgx + PostgreSQL + Redis；Vue 3 + TypeScript + Vite，前端仅位于根目录 web/。
- 首选模块化单体；按账户/协议/计费清晰分层，避免为 MVP 引入独立微服务。
- 流式响应逐块转发并支持客户端取消，不整段缓冲；在受控并发测试中验证内存增长和连接释放。
- 敏感凭据加密存储，所有管理接口授权；数据库迁移可审查、可回滚（不可逆变更需备份方案）。
- 单机部署是首要交付目标；后续扩容需要保证调度租约、账本和任务消费一致性。
- 开发和验收不使用真实付费 API 进行高频重复测试，优先采用模拟上游及确定性集成测试。

## 6. 分阶段交付与验收

| 阶段 | 交付范围 | 通过标准 |
| --- | --- | --- |
| S0 工程初始化 | 仓库结构、文档、Go HTTP 骨架、web 前端、数据库/Redis 本地容器、CI | Go 测试和前端构建通过；页面可准确显示后端存活状态 |
| S1 单渠道 MVP | PostgreSQL 模型/用户/Key、授权管理、一个原生 OpenAI 协议上游、基础请求日志 | 合法 Key 能完成非流式与 SSE 调用，非法 Key 被拒绝，断线资源可回收 |
| S2 多渠道与调度 | Anthropic/Gemini 原生接口、多个账号、路由策略、分布式并发控制 | 调度、限流、冷却、取消与失败重试通过可重复测试 |
| S3 计费与用户控制台 | 预留与结算账本、用量统计、额度与管理界面 | 重试/断线/重复消费不产生二次扣款；统计与账本可对账 |
| S4 Agent 兼容与运营 | Responses、复杂工具与思考流、跨协议转换、告警与部署优化 | 通过明确版本的客户端兼容矩阵；目标功能全部有真实集成测试 |

## 7. 当前已完成的范围

仅包含 S0 工程骨架：/healthz 与 /api/v1/system/info、web 状态页面、本地 PostgreSQL/Redis Compose 配置及构建验证配置。真实网关业务在后续阶段开发。
