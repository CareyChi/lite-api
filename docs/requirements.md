# lite-api 产品需求

项目处于 S0 工程初始化阶段。本文为产品需求基线，功能是否完成以实现和验收结果为准。

## 1. 产品定位

lite-api 是面向个人开发者、小团队及获得授权的 API 服务运营者的轻量自托管 AI 网关。独立实现 New API 所代表的多渠道聚合、统一密钥及额度管理能力，以及 Sub2API 所代表的账号池、并发限制与会话调度能力。

核心目标是兼容标准 SDK、Claude Code、Codex、OpenCode 等客户端，稳定承载长时 Agent 请求，并在不同上游之间提供可配置的模型路由、可审计的使用量和成本管理。具体兼容性以客户端版本及测试结果为准。

默认私有部署，由管理员创建用户、配置上游和分配额度。公开注册、充值支付、多租户隔离管理和独立微服务不属于首版范围。只接入获授权且符合上游服务条款的 API 或账号，不依赖伪造客户端身份、规避上游限制的实现。

## 2. 角色和业务对象

| 对象 | 责任 |
| --- | --- |
| 管理员 | 初始化系统、管理用户、模型、渠道、账号、价格、额度、路由和审计 |
| 普通用户 | 管理本人 API Key，查询被授权模型、额度、用量和请求记录 |
| API Key | 网关颁发的凭据，归属于用户，支持独立权限、有效期、限额和吊销 |
| 模型 | 面向客户端的稳定逻辑名称，具有能力、默认参数边界及价格策略 |
| 渠道（Provider） | 上游协议类型、服务地址、默认参数及网络配置 |
| 上游账号（Account） | 渠道内独立凭据、授权范围、并发、速率和健康状态 |
| 模型路由（Route） | 逻辑模型与上游模型、渠道、候选账号集合的映射及调度策略 |
| 请求 / 尝试 | 一个客户端调用和对应零至多个上游尝试，分别记录状态和用量 |

用户不等于上游账号；模型别名不等于上游模型 ID。权限分组与路由分组可以关联，但不能替代身份鉴权。

## 3. 核心需求

### FR-01 身份与权限（S1）

- 首次启动通过受控的初始化命令建立管理员，不提供公开默认密码或默认管理密钥。
- 支持管理员、普通用户及启用/停用状态；管理端会话与网关 API Key 分离。
- API Key 支持创建、摘要展示、停用、吊销、到期、模型白名单及独立限额；明文仅创建时返回一次。
- 管理动作记录审计；普通用户只能访问自己的密钥、额度和请求数据。停用和吊销须及时对所有网关实例生效。

### FR-02 渠道、账号、模型（S1 基础，S2 完善）

- 管理渠道的名称、协议、受控 Base URL、上游模型、超时和启停。
- 渠道内可配置多个账号；分别设置凭据、授权模型、并发上限、RPM/TPM、优先级、权重和冷却时间。
- 首版支持合法的上游 API Key 认证；扩展时将授权 OAuth 等凭据生命周期独立于协议解析和调度，不为不同服务商复制网关流程。
- 支持手工模型配置、别名映射和健康探测；自动模型发现属于后续增强。探测不能默认发送真实付费生成请求。
- 模型能力至少区分协议、流式、工具调用、推理、视觉、缓存、上下文/输出上限及状态型请求；模型列表仅返回当前用户有权限且已配置可用路由的模型。
- 管理员可配置明确授权的私有上游；默认限制公共上游地址、禁止元数据/控制面等受保护地址访问。

### FR-03 协议兼容（S1–S3）

- S1：OpenAI Models、Chat Completions，支持非流式与 SSE。
- S2：OpenAI Responses、Anthropic Messages、Gemini GenerateContent 和 streamGenerateContent；优先完成 Responses 与 Messages 的工具调用、推理及长流式响应。按协议支持必要的模型发现与 Token 计数能力。
- S2 内对 Responses 的 previous_response_id 等上游持久状态建立明确所有权和账号绑定；不支持的状态功能返回原生格式错误，不把状态型调用降格为无状态调用。
- 同协议默认原生透传，保留合法扩展字段、事件顺序和用量信息。跨协议转换 S3 按明确的方向和能力逐项交付，不承诺完全等价。
- WebSocket、Realtime、批处理、文件、图像生成、音频、Embedding 等按真实客户端需求另行实现，不以占位接口标记支持。
- 各协议及端点以实际样例和客户端兼容矩阵作为验收依据。

### FR-04 路由与账号池（S1 基础，S2 完整）

- 按用户授权、逻辑模型、协议和能力、启停状态、健康度、账号额度、并发及速率约束过滤候选。
- 支持优先级分层、加权调度、显式候补路由；不得静默替换成不同逻辑模型或降级推理能力。
- 使用 Redis 原子获取用户/账号相关并发租约，长时请求续租，正常结束释放，崩溃后自动回收；租约必须防止旧请求释放新持有者的槽位。
- 状态型会话严格绑定有权限的上游账号或已验证的同一状态域；普通缓存亲和仅作调度提示，不能绕过健康/权限/额度过滤。
- 区分上游认证失败、限流、容量不足、请求参数错误及网络异常；为可安全重试的错误配置退避和上限。
- 请求已可能被上游接受但结果不明时，不默认重复生成；已提交下游响应头后不跨账号重试。不得把重试成功误记为一次上游尝试。

### FR-05 限流与额度（S1 起）

- 支持用户、API Key、渠道、账号的配置化 RPM、TPM、最大并发和预算规则，按阶段实现。
- 生成前对最大输出及可计费能力做预算约束，预留额度；实际使用量可得后校准。无法界定预算的功能在有限额度模式中应明确拒绝或限制。
- 达到限制返回对应协议的错误与适用的 Retry-After。Redis 或账务数据库不可用时，拒绝新的受限付费生成，不绕过额度和并发限制。
- 请求排队仅在后续确有需求时增加，必须有长度、等待时间及取消限制。

### FR-06 用量与账本（S1 起，付费流量前完成）

- 平台支持管理员分配额度和受限/不限余额的私有用户；即使不限余额也记录使用量及实际成本。
- 区分客户端逻辑模型售卖价格与上游采购成本；保存实际应用的价格版本、计价单位和币种/内部额度单位，不默认引入外汇换算。
- 分别记录未缓存输入、缓存读取、缓存写入、输出、推理或其他适用计费项；保留供应商报告的原始用量维度，防止将包含关系的 Token 重复计价。
- PostgreSQL 中事务化预留、扣减、释放及调整，使用不可变流水、唯一幂等键、精确数值与可审计的余额快照；不得静默透支。
- 分开记录请求和每次上游尝试，明确区分成功、失败、取消、用量缺失、待对账。默认只按明确定义的用户计费结果结算，内部失败尝试的上游成本单独记录。
- 客户端断开不等同于上游未计费。没有最终用量时进入待对账状态；按有时限的明确政策处理预留、估算、差额和未知成本，不将未知当作零或真实值。
- 进程崩溃、重复提交内部结算任务、Redis 数据丢失等场景不得重复扣款。不能保证外部上游恰好执行一次，应诚实记录不确定结果。

### FR-07 管理控制台（S1 基础，S2 完整）

- S1 提供受保护的初始化/配置管理能力，至少可管理用户、密钥、渠道、模型、额度、查看请求及账本；先满足端到端调试和私有使用。
- S2 提供完整的登录、管理员与用户界面、账号池健康、模型路由、用量与费用统计、日志筛选和配置测试。
- 不显示未实现的管理功能为已可用；统计来自实际数据，敏感凭据默认脱敏且不回显。
- 前端唯一工程位于仓库根目录 web/，桌面和移动端可读可操作；管理 API 与标准模型 API 分离。

### FR-08 运维与安全（S1 起）

- 每个请求具有 request_id；记录请求与尝试的协议、模型、状态、耗时、首事件/首 Token 延迟（可测时）、用量来源、费用和脱敏错误。
- 默认不持久化完整请求/响应正文，不记录凭据、认证查询参数或完整上游错误正文；日志保留时间、统计汇总和清理可配置。
- 限制请求体、单事件大小、连接、最大流式时长及空闲超时；流式请求可取消并及时释放资源。
- 管理端密码安全哈希、上游凭据加密、访问控制、Cookie 安全属性与 CSRF 防护、SSRF 和可信反代边界均属于首版上线门槛。
- 提供存活和就绪检查、优雅停机、数据库迁移与备份恢复；当账务状态不可用时停止接收新的付费请求。
- 单机生产交付为同源 Web + Go 服务 + PostgreSQL/Redis，Docker Compose 一键部署；支持 Linux AMD64/ARM64。未来可通过共享数据库及 Redis 扩展网关实例。

## 4. 关键请求流程

1. 认证客户端，验证权限、协议、请求大小及模型。
2. 确定逻辑模型与候选路由、价格快照、请求预算；检查限流和可用额度。
3. 领取并发租约；在 PostgreSQL 事务中建立请求与预留，再持久化本次上游尝试。
4. 选择适配器，构建受控上游请求，开始转发及同步观察用量，不持有数据库长事务。
5. 按协议增量转发，在取消/失败时停止或关闭上游；只有明确允许重放的失败可以换候选。
6. 使用独立于客户端取消的有界结算上下文保存用量和状态、完成幂等结算；未完成的请求由持久化恢复任务对账。
7. 释放租约，更新健康状态与统计；使用量或费用仍不明时保持待对账标记。

## 5. 非功能及验收要求

- Go 模块化单体；协议、凭据、调度、传输、账务解耦。数据层采用 pgx v5 + sqlc、PostgreSQL 17、Goose；Redis 只承担可重建的短期状态。
- 流式转发不整段缓存生成结果，不因统一写超时切断健康长连接；限制每连接缓冲与最大时长，通过慢消费者和客户端取消测试验证资源释放。
- 使用确定性的模拟上游与真实 PostgreSQL/Redis 集成测试；测试网络中断、断流、凭据吊销、故障切换、重复结算和进程恢复。
- 性能目标以明确负载模型、并发流数、请求/响应大小、上游延迟和资源占用为基线；未进行压测前不承诺吞吐指标。
- 安全、账务、原生协议及单机部署验收通过后才允许向不可信客户端开放；不能仅凭健康检查宣称生产就绪。

## 6. 开发顺序与发布门槛

| 阶段 | 交付范围 | 验收条件 |
| --- | --- | --- |
| S0 工程基线 | 项目骨架、需求、架构、接口约定、CI、开发依赖 | 提交依赖锁文件；Go 测试、前端类型检查和构建通过 |
| S1 私有垂直 MVP | 用户/密钥、渠道模型、OpenAI Chat Completions、基础限流与路由、预留结算、请求日志、最小管理能力 | 非流式/SSE 真实转发；非法访问被拒绝；单请求多次尝试、并发预算、断线和崩溃恢复可重复验证 |
| S2 网关首版 | Responses、Messages、Gemini 原生协议，状态绑定、多账号调度、完整管理端、生产单机部署 | SDK/Agent 兼容矩阵；多账号租约与故障切换；权限隔离、账本一致性、备份恢复、安装及升级测试通过 |
| S3 能力增强 | 跨协议转换、授权凭据生命周期、模型同步、统计归档、监控告警与按需增加的端点 | 逐方向能力覆盖与流式回归；观测数据不泄密；依需求验证多实例 |
| S4 可选商业化与规模化 | 套餐、充值支付、精细 RBAC、多租户及高级路由 | 明确实际需求后立项，另定义安全、合规与一致性验收 |

S1 为内部受控试用，S2 为第一个可对外发布的业务版本。S0 已有健康接口、前端状态页与开发环境，尚无实际生成、账户或账务功能。

## 7. 后续决策

按真实产品需求再确定支付、公开注册、额外模型端点、多租户和高级账号接入方式。未实现的接口和可用性承诺不预先写入用户界面。
